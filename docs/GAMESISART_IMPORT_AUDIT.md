## 1. Введение и цели аудита

Цель аудита — детально исследовать существующий код импорта, выявить скрытые архитектурные дефекты, оценить риски дублирования данных и повреждения production базы данных, а также сформировать требования к безопасному пайплайну staged-импорта.

## 2. Анализ существующего состояния Production БД (`club_romance.db`)

В ходе аудита текущей базы данных `club_romance.db` (5 636 096 байт) были выявлены критические факты о качестве текущих данных:

1. **Массовые фиктивные плейсхолдеры**:
   - Всего в таблице `choices` находится **8 235 записей**.
   - Из них **8 223 записи (99.85%)** содержат шаблонный текст:
     `text = "Краткий пункт выбора из импортированного прохождения"`, `tags = "gamesisart_import"`.
   - Реальные тексты диалогов и развилок в базе отсутствуют — старый импортер просто нарезал абзацы текста и вставлял заглушки.
2. **Искажение URL источников**:
   - Из 54 историй в БД у **51 истории** поле `guide_source_url` указывает на общий каталог:
     `https://gamesisart.ru/guide/Romance_Club_Prohozhdenie.html` вместо индивидуальных канонических страниц историй.
   - Только 3 истории имели индивидуальные ссылки или NULL.
3. **Неполнота контента (потеря сезонов)**:
   - В истории «7 братьев» в текущей БД присутствует **только Сезон 1** (10 эпизодов, 269 плейсхолдеров).
   - Сезоны 2 и 3 в production БД полностью отсутствуют, хотя на GamesIsArt история завершена (3 сезона, 30 эпизодов, 1533 реальных выбора).

## 3. Архитектурный разбор старого импортера

В проекте обнаружены два устаревших скрипта импорта:
- `scripts/import_gamesisart_guides.py` (SQLAlchemy async)
- `scripts/import_gamesisart_guides_sqlite.py` (чистый sqlite3)

### 3.1. Примитивный HTML-парсинг
Старый импортер использовал стандартный `html.parser.HTMLParser`:
- Не строил DOM-дерево.
- Не умел различать таблицы характеристик, навигационные панели, скрипты Яндекс.Adfox и комментарии.
- Не извлекал классы CSS (`TextItem`, `TextUp`, `TextLove`, `TextDown`).
- Не поддерживал структуру списков гардероба (multi-option).
- Не определял номера сезонов для нестандартных заголовков.

### 3.2. Деструктивные операции записи
- **Удаление историй**: метод `remove_placeholders` выполнял прямой `DELETE FROM stories WHERE description LIKE '%Базовая запись добавлена для каталога%'`. При случайном совпадении описания это приводило к каскадному удалению связанных пользовательских данных (`favorites`, `progress`, `subscriptions`).
- **Неконтролируемый `ALTER TABLE`**: метод `ensure_columns` на лету выполнял `ALTER TABLE ADD COLUMN` прямо в рабочей базе без версионирования схемы.
- **Грубая перезапись выборов**: метод `replace_choices` удалял все выборы с тегом `gamesisart_import` (`DELETE FROM choices WHERE episode_id = ? AND tags LIKE '%gamesisart_import%'`), заменяя их заглушками.

### 3.3. Идентификация сущностей (Source Identity)
В старом импортере сопоставление выполнялось исключительно по строковому равенству названий:
```python
row = connection.execute("SELECT id FROM stories WHERE title = ? LIMIT 1", (title,)).fetchone()
```
- Если название на сайте менялось хоть на один символ или пробел, создавалась история-дубликат с суффиксом слага (`slug-2`).
- Отсутствовала концепция `source_key` и `canonical_url`.
- Повторный импорт с незначительным изменением заголовка приводил к дублированию историй, сезонов и серий.

## 4. Что можно переиспользовать, а что необходимо заменить

| Компонент | Текущий статус | Решение в Phase 7+ |

## 5. Анализ рисков и точек сбоя

1. **Риск случайной модификации production БД**:
   - *Решение*: Вся работа в Phase 7 ведется с отдельной базой `data/gamesisart/staging.db`. Доступ к `club_romance.db` открывается исключительно в режиме `file:club_romance.db?mode=ro` (read-only URI).
2. **Риск потери пользовательских связей при обновлении выборов**:
   - Пользователи бота могут иметь прогресс (`progress`) или избранное (`favorites`), привязанные к `episode_id`.
   - Обновление выборов внутри эпизода должно выполняться транзакционно и идентифицироваться по порядковому номеру `order_index`.
3. **Риск повторного импорта (Idempotency failure)**:
   - *Решение*: В staging-пайплайне реализован контроль `content_hash` (SHA-256 сырого HTML) и `parser_version`. Повторный запуск для неизменного источника возвращает статус `UP_TO_DATE` с нулевым числом изменений.

## 6. Требования к миграции в Production

Перед будущим переносом данных из Staging в Production необходимо:
1. Сохранить резервную копию (`club_romance.db.bak`).
2. Для совпадающих историй: обновить `guide_source_url` на канонический URL.
3. Для существующих эпизодов с плейсхолдерами (`gamesisart_import`): безопасно заменить плейсхолдеры на реальные структурированные `ChoiceDocument`.
4. Для отсутствующих сезонов (например, Сезоны 2 и 3 в «7 братьев»): создать недостающие сезоны и эпизоды.
5. Проводить импорт строго через `dry-run` валидацию.
