## 5. Архитектурная безопасность первичных и внешних ключей

### Проверка внешних ключей (Foreign Keys Audit):
1. Таблицы с зависимостями:
   - `progress` (6 пользовательских строк): ссылается на `story_id`, `season_id`, `episode_id`.
   - `subscriptions` (1 строка): ссылается на `story_id`.
   - `seasons`: ссылается на `story_id`.
   - `episodes`: ссылается на `season_id`.
   - `choices`: ссылается на `episode_id`.
2. **Входящие внешние ключи на `choices`**: **0 (ноль)**.
   - Ни одна таблица в базе данных `club_romance.db` не ссылается на `choices.id`.

### Стратегия изоляции ID (Staging vs Production):
- Первичные ключи `staging_choices.id` в `staging.db` являются **внутренними ключами staging базы** и **НИКОГДА** не переносятся напрямую в `choices.id` production базы.
- Для существующих 6 279 заглушек выполняется **in-place обновление (UPDATE)** с сохранением их оригинальных `choices.id`.
- Для новых серий и дополнительных выборов новые строки создаются через стандартный `INSERT` с генерацией новых sequential ID средствами SQLite `AUTOINCREMENT`.
- Существующие `stories.id`, `seasons.id`, `episodes.id` сохраняются неизменными. Пользовательский прогресс (`progress`) и подписки (`subscriptions`) защищены на 100%.
